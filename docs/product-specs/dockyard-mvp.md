# Dockyard MVP 产品规格

## 目标结果

让同时运行多个本机 Node 项目的开发者，在一个可信的位置导入、启动、观察、重启和诊断所有开发应用，而不再把崩溃当成黑盒问题。

## 角色与任务

- **开发者：** 找出热重载服务崩溃的原因，只重启正确的应用，并持续查看其日志。
- **Agent：** 通过 CLI JSON 确定性地查询项目/应用状态并执行有边界的生命周期操作。

## 范围

| 领域 | MVP 行为 | 验收标准 |
| --- | --- | --- |
| 导入 | 添加单个文件夹；扫描所选根目录中的 `package.json`、工作区、常见脚本和 PM2 生态配置文件 | 保存前预览发现的应用和 PM2 到 Dockyard 的转换；重复导入保持幂等 |
| 项目/应用目录 | 将文件夹建模为 `Project`，将可运行包/脚本建模为 `Application`；识别根目录启动入口 | 项目可配置自动、项目优先或模块优先启动；应用继承项目路径，但可覆盖 cwd/command |
| 生命周期 | 启动、停止、重启；发现并接管已从任意入口启动的兼容本机进程 | 已导入应用按工作目录持续发现 PID 和监听端口；状态转换可见；只有守护进程执行生命周期操作 |
| 守护 | `never` / `failure` / `always` 策略、重试预算、退避和稳定窗口 | 崩溃循环会暂停，并给出人可读原因 |
| 日志 | stdout/stderr 文件、搜索、过滤、轮转，以及通过 SSE 跟随 tail；外部进程可跟随其已重定向到本机普通文件的 stdout/stderr | 日志工作台默认按接收时间合并 stdout/stderr 并自动贴底；手动滚动后按本机设置暂停自动贴底（默认 30 秒）；UI 和 CLI 连接时先回放已保存的 tail，再跟随选中流；日志行不写入数据库；终端和匿名 pipe 不会被伪造为可读取日志 |
| 可观测性 | 进程 CPU/RSS、运行时长、重启次数、退出码、启动耗时 | 仪表盘展示每个应用/项目当前和 24 小时聚合指标 |
| 设置 | 保留期、限制、策略预设和状态目录 | 变更有版本记录并能安全应用 |
| UI 系统 | 中文/英文与浅色/暗色主题；五个核心入口：总览、项目、排障、日志、报表 | 切换立即生效并在本机持久化；没有登录、账户或用户管理 UI |
| CLI | 安全的读取操作直接执行；生命周期操作调用守护进程命令 | `--json` 输出稳定，脚本无需解析终端文本 |
| 启动体验 | 开发和生产均由单个 Nest 守护进程托管 Web 面板；CLI 可安装为本机全局命令 | `pnpm dev` / `pnpm start` 只启动一个服务进程；`dockyard --help` 可在任意目录执行 |

## MVP 明确不做

- 远程部署、多机器协同、容器、用户账户和云端日志投递；
- 任意非 Node 运行时插件（仅设计扩展点）；
- 在 SQLite 中对日志进行全文索引。

## 核心旅程

1. 扫描工作区 → 查看模块候选、项目根启动入口和 PM2 转换预览 → 调整启动偏好/命令/策略 → 保存 → 以项目入口或选中模块启动。
2. 一个由文件监听驱动的应用（无论是否由 Dockyard 启动）退出 → 守护进程记录原因 → 判断退避策略 → 重启或暂停 → UI 呈现时间线和相关日志尾部。外部进程已重定向到普通本机文件的 stdout/stderr 会被跟随并复制到 Dockyard 本机日志；终端和匿名 pipe 无法在事后安全读取，日志页即使存在历史回放也必须如实标记此状态，并提供经确认的“接管并重启”入口。
3. 开发者发现失败应用 → 打开已过滤的实时日志 → 单次重启或修改策略 → 验证健康启动耗时。
4. Agent 运行 `dockyard app status --json` 或 `dockyard logs tail <id> --jsonl`，并基于类型化输出执行操作。
5. 开发者导入已有 `ecosystem.config.*` → 审核字段映射和不支持项 → 只接受需要的应用。
